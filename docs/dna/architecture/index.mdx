# DNA v2 architecture

DNA separates ingestion and durable storage from the workers that serve data.
It reads Starknet through JSON-RPC, optionally uses WebSocket notifications to
trigger ingestion, and serves filtered blocks over the [DNA gRPC
protocol](/docs/dna/protocol).

```txt
Starknet JSON-RPC / WebSocket
             |
             v
          Ingestion <------> Etcd: coordination and mutable pointers
             |                         ^
             v                         |
        Object store <----------> Stream workers ---> Indexers
             ^
             |
     Compaction and pruning
```

Bulk block data lives in object storage. Etcd holds coordination state, leases,
and pointers that let services discover new blocks and chain reorganizations.
The object store can use AWS S3-compatible storage, Azure Blob Storage, or
Google Cloud Storage.

## DNA service

### Ingestion service

The ingestion service fetches blocks, receipts, and state updates from Starknet.
It tracks the canonical chain and detects reorganizations. An etcd lease ensures
only one ingestion instance is active for a deployment; another instance can
take over when the lease is released or expires.

Each block is split into fragments:

| Fragment | Purpose |
| --- | --- |
| Header | Block metadata encoded as protobuf |
| Body | Transactions, receipts, events, messages, traces, and state changes |
| Index | Look up matching items without decoding every body message |
| Join | Find related items, such as the transaction and receipt for an event |

Body messages are stored as serialized protobuf so stream workers can copy
matching data into responses without serializing it again.

Optional ingestion features depend on the server configuration:

- `--starknet.ingest-traces` (`STARKNET_INGEST_TRACES`) enables transaction traces.
- `--starknet.ingest-pre-confirmed` (`STARKNET_INGEST_PRE_CONFIRMED`) enables
  pre-confirmed blocks. These are refreshed while following the chain's head
  and exposed through the protocol's `pending` finality. They are not a raw
  mempool feed.

Both options are disabled by default. Requesting traces or pending finality
cannot make data available if the server did not ingest it.

### Compaction service

Compaction combines finalized blocks into segments, grouped by fragment type.
For example, an event segment contains event data from several blocks. Group
indices cover multiple segments so workers can skip blocks that cannot match
a filter.

Compaction reduces the number of object-store reads needed for historical
indexing. It does not change the stream protocol or block cursors.

### Pruner service

Pruning removes individual block objects after their data has been compacted.
The same historical data remains available in segments.

### Object hierarchy

Object storage contains four main categories:

| Prefix | Contents |
| --- | --- |
| `blocks/` | Individual blocks and generations of pre-confirmed data |
| `chain/` | Canonical-chain history used to detect reorganizations |
| `segments/` | Compacted fragments, including `transaction`, `receipt`, `event`, and `trace` |
| `groups/` | Indices covering multiple segments |

See the server's [block-store implementation](https://github.com/software-mansion-labs/starkstream-dna/blob/main/common/src/block_store.rs)
and [Starknet fragment definitions](https://github.com/software-mansion-labs/starkstream-dna/blob/main/starknet/src/fragment.rs)
for exact keys and fragment names. Persisted identifiers are part of the
[compatibility contract](https://github.com/software-mansion-labs/starkstream-dna/blob/main/docs/compatibility.md).

### Stream service

A stream worker validates and compiles each request into index lookups. It then
reads matching fragments, includes any requested related data, and sends the
result to the client. Etcd updates notify it about newly ingested blocks,
finality changes, and reorganizations.

Workers cache object-store data in memory and on local disk. This reduces
latency and repeated reads without requiring each worker to keep a full copy of
the chain. Additional workers can serve the same shared data.

For package boundaries and server development, see the [DNA
repository](https://github.com/software-mansion-labs/starkstream-dna) and its
[architecture reference](https://github.com/software-mansion-labs/starkstream-dna/blob/main/docs/architecture.md).
